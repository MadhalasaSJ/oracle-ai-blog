Locking Down Rows, Not Just Tables: Implementing Oracle Label Security

Notes from a project where "can this user see the table" wasn't a fine enough question, and we needed "can this user see this specific row" instead.

Madhalasa SJ · From a recent implementation

Most of the database security work I've written about so far comes down to a fairly binary question: can this person touch this table, yes or no. Database Vault, encryption, auditing, it all assumes that once you're inside a table you're seeing everything in it. That assumption broke down for me on a recent project pretty quickly.

There were two things going on at once. One was a customer data set where different processing purposes, marketing emails, analytics, third party sharing, each needed their own consent trail, and a customer could say yes to one and no to the other two. The other was an internal HR search tool where employees in different countries needed to see their own region's staff records and nothing else, without maintaining a separate view or a separate query per country. Neither of these is really a "can you access the table" problem. Both are "can you see this specific row, based on who you are, right now." Oracle Label Security ended up being the answer to both, which surprised me a little since I'd mostly seen it described in the docs in government and defense terms, not consent management.

What OLS actually does

The idea is simple once you get past the government and defense language the documentation leans on. OLS compares a label sitting on a row against a label, or a set of authorizations, belonging to whoever's running the query, and decides whether that row comes back or not. It's close in spirit to Virtual Private Database, both filter rows before you ever see them, but you're not writing a policy function per table here. You set up levels, compartments, and groups once for a policy and OLS does the row by row check on its own from then on.

The label itself lives in a hidden column that gets bolted onto the table the moment a policy is applied to it. You won't notice it on a plain SELECT * unless you go looking for it specifically, but it's there on every row, checked on every read and write.

Where it sits in the stack: OLS runs after Oracle has already confirmed you have ordinary object privileges on the table, and after any VPD policy has already had its say. It's one more filter layered on top, not a replacement for grants.

Levels, compartments, groups

A label has three parts and only one of them is actually required.

  • Level, mandatory. A single ranked value for how sensitive the row is. Higher number, more sensitive.
  • Compartments, optional, for splitting data at the same level by subject matter. Two rows can be equally sensitive but belong to completely different categories.
  • Groups, optional, and unlike compartments these are hierarchical. They represent ownership, usually a team, region, or business unit, and access to a parent group carries down to its subgroups automatically.

A label reads as LEVEL:COMPARTMENT1,COMPARTMENT2:GROUP1,GROUP2. Users don't get one fixed label the way rows do. They get a range instead, a minimum level, a maximum level, a list of compartments they're cleared for, a list of groups. Within that range they operate with a session label at any given moment, and it's the session label that gets checked against the row, not the full range they're authorized for. I didn't fully get this the first time I read it. It only clicked once I saw two accounts with wildly different authorization ranges land on almost identical results because their session labels happened to overlap for that particular query.

Handling consent, not just access

For the customer data piece I built the policy around a consent lifecycle instead of a rigid hierarchy, which honestly made it click faster for the rest of the team too. The levels marked where a customer sat in that lifecycle, CNST for actively consented, ANON for anonymized, FRGT for a forget-me request in progress, and NCNST for anyone who'd never consented or had pulled back consent later.

Groups did the actual heavy lifting though. Instead of one flat "consented" bucket, we had a group per channel a customer could opt into on its own: EMAIL, POST_MAIL, WEB_ADS, CAMP_MGMT, ANALYTICS, THIRDPARTY, and combination labels for anyone who'd said yes to more than one, something like CNST::EMAIL,ANALYTICS for a customer who'd allowed both email marketing and analytics but nothing else. A row carrying that label simply never showed up for a service account that wasn't cleared for both groups.

The accounts on the reading side mirrored the teams that actually touch this data day to day. The core data processing account had the full CNST to NCNST range so nothing was ever hidden from it. A separate account used only by the forget-me workflow was capped to the ANON to FRGT range and nothing above it. Marketing had EMAIL and only EMAIL. The analytics account sat at ANON level, ANALYTICS group, nothing else. And whatever fed the third party sharing pipeline got CNST level, THIRDPARTY group, full stop.

Once real rows carried these labels (something like 200 rows tagged CNST::ANALYTICS, 123 tagged CNST::EMAIL, a small handful tagged with both, a handful more sitting at FRGT, the rest at NCNST) the counts lined up exactly the way I'd expect the moment each account queried with its own session label instead of a wide open one.

The right to be forgotten, without deleting anything

This is the piece I keep bringing up when people ask why we bothered with OLS instead of just adding a status column and filtering on it in the application. We wrapped the relabeling in a single stored procedure, forget_me(customer_id), so nobody handling a forget-me request ever has to touch label syntax by hand. Before I ran it against a test customer, the FRGT count sat at 5.

exec forget_me(100)

PL/SQL procedure successfully completed.

FRGT went to 6, and a quick follow-up query showed exactly which records had shifted, by ID, name, email, the works, including the customer I'd just run it against. Nothing got deleted anywhere. Only the row's label changed, and that's a genuinely different kind of update than touching a normal column, it happens through the label mechanism rather than an UPDATE against a value the app would ever see directly. Every account whose authorization no longer covered that new label lost visibility into the row instantly, and none of the application code had to change to make that happen.

Wiring it into an HR search application

The second piece lived inside an existing HR employee search tool built on a Java Glassfish stack, and this is where OLS actually had to earn its keep underneath a real application instead of just answering nicely at a SQL prompt.

OLS metadata is scoped per pluggable database in a multitenant setup, and you can't create policies at the CDB root or the application root, so before touching anything else I checked that OLS was actually configured and enabled where the application's schema lived. It's the kind of thing that's easy to assume is fine and then lose an afternoon to later. Once that checked out, the policy went in with levels for departments (IT, FIN, HR) and groups for geography and business units (GBL for global, plus USA, EU, GER, LTM, CAN).

The schema owner running the application's queries got the broadest possible label, essentially TO_DATA_LABEL('...', 'HC:IT,FIN,HR,IP:GBL,USA,EU,GER,LTM,CAN'), since it needs full visibility before the application layer does anything with the results. Two individual employee accounts got much narrower labels instead, one scoped to the EU and Germany groups, and one scoped to Canada only.

Employee rows were labeled by relabeling the hidden column based on each employee's city, mapped up to the appropriate country group:

Once the policy was actually applied to the table, enforcement went live, and a distribution check across cities (Berlin, Costa Mesa, London, New York, Paris, Santa Clara, Sunnyvale, Toronto) confirmed the row counts matched what had been labeled, nothing lost, nothing double-counted.

Same query, two very different results

Watching this part actually work end to end is what got the rest of the team on board. With the policy live, the exact same employee table gave back completely different results depending on who was logged in, and the search query itself never changed a single character.

The schema owner, deliberately given the "sees everything" label, got the full employee count back across all cities. A Canada-scoped account, querying the identical table through the identical search page, came back with a fraction of that count, and every single row belonged to the Toronto office.

OLS_READ_LABEL
--------------
P::CAN

COUNT(*)
--------
     162

CITY       COUNT_CITY
--------   ----------
Toronto           162

The EU-scoped account behaved the same way in reverse, coming back restricted to German-labeled rows. Same search form, same underlying SQL, same JSP pages. Different logged-in user, different slice of the table, and nobody had to add a WHERE clause anywhere in the application to make that happen.

Making that hold at the application layer, not just at a database prompt, meant adding one call in the login flow to a small procedure that sets the application user's OLS label as soon as they authenticate, before any search query runs on their behalf:

CallableStatement stmt2 = null;
String sql = "{call employeesearch_prod.set_app_user_label ( ? )}";
stmt2 = conn.prepareCall(sql);
stmt2.setString(1, oLoggedUser);
stmt2.executeQuery();

After that call was in place and the application server was cycled to pick up the change, logging in as a German HR user versus a Canadian HR user against the identical search page produced visibly different employee lists, with the search query in the JSP code completely untouched.

What I'd tell myself before starting

A few things I keep coming back to, mostly because none of this was obvious to me before I actually built it.

  • Authorization range versus session label sounds like a technicality until you're the one designing the policy. A user can be cleared for a lot and still be running with a much narrower session label at any given moment, and that's the thing actually deciding what they see, not the full range on paper.
  • Don't mix up what compartments are for versus groups. Compartments split things at the same sensitivity level, that's what the consent channels were doing. Groups are about ownership and they nest, which is what made the country and region setup work for the HR side.
  • Enforcing this in the database rather than trusting the application layer to filter correctly means a sloppy query somewhere in the JSP code can't accidentally hand back a row someone shouldn't see. I like that a lot more than hoping every developer remembers to add the right WHERE clause every time.
  • Check the OLS configuration status per PDB before assuming anything works. I almost didn't, and it would have cost me a confusing afternoon later.

Consent management and HR access control don't look like the same problem on the surface, but once I'd built both I realized I was reusing the exact same three ingredients each time, just relabeled for the situation. Next thing on my list is figuring out how this plays with Data Redaction and Database Vault, since apparently the same clearance concept is supposed to carry across all three.
